# 目录布局与文档分工

## 两层

外层是**工程层**（= App 会话分组名 = `projects/<工程名>/`），内层是**完整技能目录**。
两层同名即可（`projects/a-new-skill/a-new-skill/`），不需要另起工程名——部署脚本认的是「含 SKILL.md 的子目录」，工程文件放在外层永远不会混进部署产物。

**`docs/`、`temp/` 一律创建**；空目录用 `.gitkeep` 占位（git 不跟踪空目录）。

**`assets/` 是可选目录，首次生成不建**：只在脚本真的要读模板、图标、字体时才创建。不预建的理由是先占一个空目录会让人误以为“这里该有东西”，实际多数技能用不到。

目录树不在这里复述：`normalize.py --apply` 建出来的就是标准结构。

技能目录里的四个位置各自回答不同问题：
`SKILL.md` 怎么用 · `references/` 参数与边界 · `scripts/` 能力 · `tests/` 回归。

## 工具脚本只有一份

`deploy.py`、`validate.py`、`normalize.py` 都在本技能的 `scripts/` 里，**不复制到各个工程**：

```sh
python3 /var/minis/skills/skill-generator/scripts/deploy.py            # 在工程目录下执行
python3 /var/minis/skills/skill-generator/scripts/deploy.py --project <工程目录>
python3 /var/minis/skills/skill-generator/scripts/validate.py <技能目录>
python3 /var/minis/skills/skill-generator/scripts/normalize.py [工程目录]
```

原因：副本必然漂移——`quota-usage` 工程里那份 `deploy.py` 就停在“无打包”的旧版本，而主版本已经加了打包与归档。工具改一次，所有工程立即用上，不用逐个同步。

工程目录里**不再有** `deploy.py`；`deploy.py` 默认以当前工作目录为工程根，也可用 `--project` 指定。

## 每个文件回答什么

| 文件 | 回答的问题 | 读者 | 改动频率 |
|---|---|---|---|
| `SKILL.md` | 怎么用、命令、输出怎么读 | 我（加载时） | 低 |
| `CHANGELOG.md` | 每个版本改了什么 | 用户（升级前） | 每版 |
| `references/` | 参数、退出码、边界 | 我（按需） | 低 |
| `PROJECT.md` | 为什么这样设计 | 人 | 低 |
| `PROGRESS.md` | 现在到哪、下一步 | 任何 chat / 人 | 高 |
| `docs/` | 调研结论、接口清单、长文档 | 人 | 偶发 |
| `temp/` | 中间稿 | 我 | 高频 |
| `git log` | 逐次提交 | 人 | 每次 |

**技能目录里不放**：`PROJECT.md`、`PROGRESS.md`、`README.md`、临时文件、`.git`（`README.md` 只在要发 GitHub 时加）。

## CHANGELOG.md 怎么写

**必须带、随技能发布**：它服务于技能使用者（这一版值不值得升），不是工程接手者（那看 `PROGRESS.md`）。放在**技能目录内**，`deploy.py` 会一起推上线。

三层结构，从上到下依次变细：

```
1.6.0 · 2026-11-23           ← 版本行：纯文本，不加 #，中间用 ·

技能规范（新）                 ← 分组标题：功能点名称 +（新 / 改 / 修），独立成行
- 检查命名：工程目录名对 App 分组名、技能目录名对 name；不一致只说明该改成什么。

发布流程（改）
- 分两轮：第一轮只把变更记录贴在对话正文并结束，确认后才提交与上线。
- 测试时机：修改阶段只写用例、不跑；发布前统一跑。

撤销与回滚（新）
- 合成一件事：提交与线上都退回上一版，改动全部保留。
```

规则：

| 项 | 规定 |
|---|---|
| 版本行 | `x.y.z · YYYY-MM-DD`，纯文本不加 `#`，降序，最新在最上；最新版本号必须等于 `SKILL.md` 的 `version` |
| 分组标题 | **功能点名称 + 括号标注**，独立成行：`技能规范（新）`、`发布流程（改）`、`工程结构（修）`；空组不写 |
| 功能点命名 | 优先用功能表里的名字；跨功能的按主题命名（发布流程 / 撤销与回滚 / 提交规范 / 变更记录 / 工程结构 / 功能表） |
| 标注 | `新`＝新增功能点，`改`＝行为变化，`修`＝修 bug 或修自相矛盾 |
| 条目 | `- 小标题：详细内容`，写清「改了什么、能干什么」，一条一件事 |
| 不写什么 | 测试用例、覆盖率、重构细节、依赖升级、错字；分组也不设「测试」。但**测试时机与流程**的变化要写 |
| 不加顶层标题 | 文件第一行就是最新版本行，不写 `# 变更记录` |
| 不设未发布区 | 没有确定版本的内容不写进来；版本号在改代码前就定 |

格式由 `validate.py` 检查（版本一致、降序、分组标注、条目冒号）。**内容判断**留给写的人：
一条改动用户能不能感知、该归到哪个功能点，工具判定不了。

**为什么强制**：只有 `version` 一个数字时，用户升级前无法判断值不值得升，`git log` 外人又看不到。变更记录是唯一给使用者的说明。

**怎么保证 commit 前加好**，分两段：

| 阶段 | 做什么 |
|---|---|
| 修改（授权「改」） | 改内容 → 顶部加版本行与条目 → 同步改 `version` → 补测试用例。**只写不跑** |
| 发布（用户确认） | 跑 `validate.py` → 跑 `tests/run.py` → commit → deploy（deploy 会再校验一次） |

**例外**：技能新建、技能规范刚做完时，**立即跑一次 `validate.py`** 验收产出物；这是验收不是日常修改。

## docs/ 放什么

`docs/` 是**沉淀层**：从 `temp/` 里捞出来、值得留下来的东西。判断标准是「下一个接手的人会不会想读」。

| 放 | 不放 |
|---|---|
| 接口调研：端点清单、字段含义、分页/鉴权坑 | 进度流水（`PROGRESS.md`） |
| 外部规范摘录：平台文档、政策公告、计费规则 | 一句话决策（`PROJECT.md`「关键决定」） |
| 长文档：超过 `PROJECT.md` 篇幅的设计说明 | 技能运行时要查的参数（技能 `references/`） |
| 排障记录：某次异常的现象 → 根因 → 解法 | 原始响应体、截图、抓包（`temp/`） |
| 历史开发日志（某平台当初怎么做的） | 待办清单（`PROGRESS.md`「待办」） |

四条硬规则：

1. **文件名带主题**：`<主题>-<类型>.md`，如 `minekuai-api-research.md`、`qiniu-quota-fields.md`；不用 `notes.md`、`README.md`（会与工程根冲突）。
2. **开头三行给结论**：日期 + 一句话结论 + 适用版本，读完前三行就知道要不要继续读。
3. **必须在 `PROJECT.md` 里被引用**：`docs/xxx.md` 出现在 `PROJECT.md` 里，否则没人找得到；`validate.py` 对未引用的 docs 报 WARN。
4. **历史材料要标注**：写于架构变更之前的文档，开头注明「历史记录，当前入口是 ……」，避免被当成现行说明。

**`temp/` → `docs/` 的沉淀路径**：调研在 `temp/` 里进行（原始响应、草稿、试错），结论稳定后重写成 `docs/<主题>.md`（结论前置），再在 `PROJECT.md` 里挂一行引用，`temp/` 里的原稿就可以删。

技能运行时要查的东西（参数表、退出码、接口速查）放**技能的 `references/`**，不放 `docs/`——前者会被加载进上下文，后者不会。

## 临时文件落点

| 用途 | 放哪 | 进外层 git | 生命周期 |
|---|---|---|---|
| 工程相关的抓取数据、中间稿 | `projects/<工程>/temp/` | ✅ 记录变动 | 沉淀完可删 |
| 一次性测试沙盒 | `/tmp/<技能名>-test/` | ❌ | 容器重启即失效 |
| 跨会话要留（配置、状态） | `/var/minis/shared/<话题>/` | ❌ | 长期，0600 |

**`temp/` 进外层 git**：留下「试过什么、拿到了什么」的痕迹，出问题能回看原始数据。
不挡大文件——图片、压缩包都是证据；只排除 `__pycache__/`、`*.pyc`、`.DS_Store`。

工程层 `.gitignore` 只有一条实质规则：排除技能目录（`/<技能名>/`，多个写多行）。
模板由 `normalize.py` 生成，不要手写 `/*/`——实测它会连 `docs/` 一起排除，写进去的内容静默丢失。

提交用 `chore(temp): <一句话>`，与代码提交分开。

**临时文件绝不写进技能目录**——它会被 `deploy.py` 一起推上线。

## PROJECT.md 与 PROGRESS.md

两个文件由 `normalize.py` 按实际技能名生成，**模板不在文档里复述**——复制过来只会和代码里的版本漂移。
改这两份文件的唯一规矩：

| 文件 | 写什么 | 什么时候改 |
|---|---|---|
| `PROJECT.md` | 定位、功能点、关键决定（写“曾经→结果→所以”）、目录、上线链路、遗留 | 决策变化时；踩坑或取舍就追加一条 |
| `PROGRESS.md` | 当前状态（版本、可用、已知问题、下一步）、待办、时间线 | 当前状态**原地改写**；时间线**只追加**，一条 ≤5 行 |

- 「关键决定」只写在 `PROJECT.md`；`PROGRESS.md` 里只留一句结论 + `理由见 PROJECT.md`，两份都写完整版必然一边过期。
- 时间线长到 100 行左右就压缩：同一版本系列合并成一条，细节指向 `git log`。
- 内容判断的标准：读的人能不能一眼知道“现在能不能用、还差什么”。

## 什么时候改、什么时候提交

**要不要改本身由用户决定**：只有用户明确表示要改才动技能文件；讨论阶段的产出写到工程层 `temp/`，
不写进技能目录。工程层的记录与工具文件不需要授权。

**改了不等于提交，更不等于发布**：改动留在工作区，等发布时由 `release.py` 一次做完。

节奏不再靠表格记：`release.py status` 报当前阶段（改中 / 待发布 / 已同步），
`prepare` / `confirm` 强制走完确认与提交的顺序。这里只留一句需要人判断的：

- **值得留的结论才沉淀**：换个 chat 还能用上，且不是从代码里一眼能读出来的，才写进 `docs/`；否则留在 `temp/`。
