DeepSeek-Stack 统一技能入口。每条用户消息先通过 ds-help 路由，读取命中技能的完整上游原文并严格执行。使用脚本状态机记录路由、读取、执行和验证过程，确保工作过程可追踪、可审计、可复核。

# DeepSeek-Stack Workflow

## 功能

| 功能 | 什么时候用 | 及格线 |
|---|---|---|
| 路由 | 每条用户消息 | 读 `references/ds-help.md`，记录命中的技能 |
| 读取 | 路由给出技能后 | 读该技能完整原文，`workflow.py read` 留记录 |
| 执行 | 原文读取完成后 | 按原文执行，`workflow.py run` 记录命令与退出码 |
| 验收 | 每轮结束前 | `workflow.py verify` 通过后才能 `stop` |

## 1. 核心原则

本 Skill 是 `aicodeking/deepseek-stack` 的统一工作入口。

`references/` 保存上游提供的 29 份 `ds-*` 技能原文。每份原文独立保存，保留原有文件名、技能名称、内容、步骤和约束。

本 Skill 负责统一路由、原文读取、执行管理、状态记录和结果验收，不取代、不改写、不合并上游技能。

必须遵守以下原则：

1. 每条用户消息独立路由，不沿用上一轮的路由结果。
2. `references/ds-help.md` 是专项技能路由的唯一依据。
3. 命中技能后，必须读取对应的完整原文。
4. 必须执行所有适用的技能要求，不得随意跳过步骤。
5. 使用 `scripts/workflow.py` 记录工作流状态和执行证据。
6. 所有完成状态必须有实际证据支持。
7. 不得把计划执行、口头声明或状态猜测当作真实执行结果。
8. 不得将脚本状态机描述为 Minis 原生 Hooks 或自动拦截机制。

## 2. 每轮消息强制路由

### 2.1 创建本轮工作记录

每条用户消息开始处理时，首先创建独立工作轮次：

```bash
python scripts/workflow.py start
```

脚本为本轮生成唯一 `turn_id`，创建对应的状态文件：

```text
.state/turn-<id>.json
```

每轮使用独立状态文件，不得覆盖、复用或混淆其他轮次的记录。

### 2.2 读取路由规则

必须实际读取：

```bash
cat references/ds-help.md
```

完整阅读 `ds-help.md`，根据用户当前消息判断适用技能。

不得仅凭技能名称、历史对话、模型记忆或个人经验代替路由表。

读取后在工作回复中写明路由依据：

**调用 ds-help：进行路由**

这次读取必须单独发起一次工具调用，不能和 `start`、`route` 或其他命令合并。工具调用的标题就写上面那一行，用户要能在卡片上直接看到。

### 2.3 确认路由结果

确定命中的技能后，记录本轮路由：

```bash
python scripts/workflow.py route <技能名>
```

技能名必须使用上游原始名称，包括 `ds-` 前缀。

在工作回复中使用以下标题格式：

**路由到 <技能名>：读原文**

如果命中多个技能，逐个记录，按照依赖关系和执行顺序排列。

如果没有适用的专项技能，明确记录本轮无技能命中，不得为了形式强行调用某个技能。

## 3. 命中技能后强制读取原文

### 3.1 读取完整文件

每个命中的技能都必须读取对应的完整原文。

例如：

```bash
cat references/ds-mode.md
cat references/ds-blueprint.md
cat references/ds-verify-loop.md
```

实际读取路径必须与命中的技能名称一致。

### 3.2 记录读取结果

完成文件读取后，执行：

```bash
python scripts/workflow.py read <技能名>
```

读取记录应由脚本根据实际文件内容生成，至少包括：

- 当前 `turn_id`
- 技能名称
- 原文文件路径
- 文件内容摘要
- 文件大小或读取范围
- 读取时间
- 读取结果

只有真实读取成功，才能记录为 `READ_DONE`。

不得通过模型自行声明、手工填写状态或伪造摘要来冒充读取成功。

### 3.3 读取失败处理

如果文件不存在、读取失败、内容不完整或无法确认读取完整性：

1. 不得声称已完整读取。
2. 不得根据猜测补写上游技能要求。
3. 将本轮标记为阻塞或失败。
4. 向用户说明具体原因。
5. 在问题解决前，不得宣称该技能已完成执行。

## 4. 严格执行上游技能

读取完成后，必须以对应 `ds-*.md` 原文作为执行依据。

完整遵守原文中的所有适用要求，包括但不限于：

- 适用场景和触发条件
- 前置条件
- 工作流程
- 操作步骤
- 命令和工具使用要求
- 文件结构和命名约束
- 代码规范
- 测试和验证要求
- 质量检查
- 禁止事项
- 异常处理
- 停止条件
- 交付要求
- 完成验收标准

不得为了提高速度而擅自删除、合并或跳过关键步骤。

不得把技能原文中的建议擅自升级成绝对规则，也不得弱化原文明确规定的强制要求。

如果某项要求不适用于当前任务，应根据原文的适用条件判断，并在需要时说明不适用的原因。

### 4.1 多技能协作

一个任务命中多个技能时：

1. 分别读取每份技能原文。
2. 分别记录读取结果。
3. 根据技能之间的依赖关系确定执行顺序。
4. 保留每个技能各自的职责和验收要求。
5. 不得将多个技能的要求混合成一个未经定义的新流程。
6. 完成一个技能的要求后，再进入依赖它的后续步骤。

例如，任务同时涉及工作模式、架构设计和代码验证时，应分别执行 `ds-mode`、`ds-blueprint` 和 `ds-verify-loop` 的适用要求。

### 4.2 技能冲突处理

当多个技能要求发生冲突时：

1. 先检查各自的适用范围。
2. 检查是否存在前置条件或依赖关系。
3. 优先遵守更具体且适用于当前任务的要求。
4. 不得自行删除任何一方的关键约束。
5. 如果冲突无法合理解决，停止冲突部分的执行并向用户说明。

## 5. 工作流状态机

### 5.1 状态定义

每轮工作使用独立状态机。

状态如下：

| 状态 | 含义 |
|---|---|
| `ROUTE_PENDING` | 已创建本轮记录，等待路由 |
| `ROUTE_DONE` | 已完成路由并记录技能 |
| `READ_PENDING` | 等待读取命中技能原文 |
| `READ_DONE` | 已完成所有命中技能的原文读取 |
| `EXECUTING` | 正在执行技能要求 |
| `EXECUTED` | 已完成适用的执行步骤 |
| `VERIFYING` | 正在进行结果验证 |
| `VERIFIED` | 已完成验证且证据符合要求 |
| `BLOCKED` | 因缺少条件、权限或依赖而无法继续 |
| `FAILED` | 执行或验证发生失败 |
| `COMPLETED` | 本轮工作通过验收并完成 |

### 5.2 状态迁移

正常流程：

```text
ROUTE_PENDING
    ↓
ROUTE_DONE
    ↓
READ_PENDING
    ↓
READ_DONE
    ↓
EXECUTING
    ↓
EXECUTED
    ↓
VERIFYING
    ↓
VERIFIED
    ↓
COMPLETED
```

异常流程：

```text
任意未完成状态
    ├── BLOCKED
    └── FAILED
```

状态迁移必须符合实际执行顺序。

不得：

- 未路由就记录读取完成。
- 未读取原文就记录执行开始。
- 未执行就记录执行成功。
- 未验证就记录验证通过。
- 在存在未解决的阻塞或失败时记录正常完成。
- 通过手工修改状态文件绕过状态迁移规则。

### 5.3 状态管理命令

统一通过以下脚本管理状态：

```bash
python scripts/workflow.py start
python scripts/workflow.py route <技能名>
python scripts/workflow.py read <技能名>
python scripts/workflow.py run <cmd>
python scripts/workflow.py verify
python scripts/workflow.py stop
```

所有命令必须针对当前轮次执行。

脚本负责校验状态迁移，拒绝不符合前置条件的操作，并记录实际执行结果。

`run` 应由脚本实际执行传入的命令，并记录命令内容、执行时间、退出码和输出摘要。

`read` 应由脚本实际读取指定技能文件，并记录文件路径、内容摘要和读取结果。

`verify` 应根据实际验证证据判断结果，不得仅凭模型口头声明判定通过。

`stop` 应检查本轮状态、技能执行记录和验证证据，符合验收条件后才能将状态设置为 `COMPLETED`。

### 5.4 状态文件

每轮状态文件位于：

```text
.state/turn-<id>.json
```

状态文件至少记录：

```json
{
  "turn_id": "唯一轮次标识",
  "status": "ROUTE_PENDING",
  "created_at": "创建时间",
  "updated_at": "更新时间",
  "routes": [],
  "reads": [],
  "executions": [],
  "verifications": [],
  "blockers": [],
  "failures": [],
  "completion": null
}
```

实际状态文件由脚本维护。

记录必须与真实操作对应，不得把计划、推测或未执行的操作写成已完成事件。

历史轮次记录必须保留，不能为了让当前轮次通过验收而删除失败或阻塞记录。

## 6. 证据与审计

### 6.1 证据来源

工作流记录必须基于真实操作产生的证据。

有效证据包括：

- 实际执行的命令
- 命令退出码
- 实际读取的文件
- 文件内容摘要
- 实际生成或修改的文件
- 测试运行结果
- 验证工具输出
- 实际产生的错误信息
- 用户明确提供的授权或确认

### 6.2 区分事实与声明

以下状态必须严格区分：

| 表述 | 代表的事实 |
|---|---|
| 已计划 | 仅有执行计划 |
| 已尝试 | 已发起实际操作 |
| 已执行 | 操作已完成，有执行记录 |
| 已读取 | 文件已实际读取，有读取记录 |
| 已验证 | 验证步骤已执行，有验证证据 |
| 已完成 | 所有适用要求均通过验收 |

不得将“准备执行”描述成“已经执行”。

不得将“命令已发出”描述成“命令成功”。

不得将“文件存在”描述成“文件内容正确”。

不得将“脚本记录成功”描述成“所有外部行为均被强制执行”。

### 6.3 审计记录

用户可以通过以下命令检查历史轮次：

```bash
ls .state/
cat .state/turn-<id>.json
```

审计时应重点检查：

- 本轮路由了哪些技能。
- 每份技能原文是否有真实读取记录。
- 是否记录了实际执行的命令。
- 命令退出码是否成功。
- 是否存在失败或阻塞。
- 验证是否有实际证据。
- 最终状态是否符合迁移规则。

状态文件是工作流的审计记录，不是对模型全部行为的自动监控证明。

## 7. Minis 环境中的执行边界

本工作流使用脚本状态机，不依赖 Minis 原生 Hooks。

`workflow.py` 是显式调用的工作流管理工具，不是自动注入的工具调用拦截器。

必须明确以下边界：

1. 状态机能够记录实际提交给它的操作。
2. 状态机能够校验其管理范围内的状态迁移。
3. 状态机能够执行被提交给 `run` 的命令并记录结果。
4. 状态机不能自动拦截所有未经它调用的工具操作。
5. 状态机不能证明不存在未记录的操作。
6. 状态机不能保证模型永远不会遗漏脚本调用。
7. 状态文件不能单独证明整个执行过程没有绕过工作流。

因此，每轮工作都应主动调用工作流脚本，并在最终验收时核对实际操作与状态记录。

不得使用以下不准确表述：

- Hooks 已自动拦截所有工具调用。
- 所有工具调用都不可绕过。
- 状态文件证明模型没有遗漏任何操作。
- 脚本能够自动监督所有模型行为。

统一使用以下准确定位：

**本项目通过显式调用的脚本状态机，实现工作流程记录、状态迁移校验和执行结果审计。**

## 8. 上游原文保护

`references/` 中的 29 份 `ds-*` 文件是上游原始技能内容。

必须遵守：

1. 保留全部原始文件。
2. 保留所有原始文件名。
3. 保留所有 `ds-` 技能名称。
4. 保留原文的步骤、规则、限制和验收要求。
5. 不得将多份技能合并成一个混合技能。
6. 不得为了适配本统一入口而擅自改写原文。
7. 不得以摘要代替完整原文。
8. 不得在没有用户明确授权的情况下修改上游技能文件。

统一入口只负责路由、调度、状态记录和执行验收。

如果需要修复、升级或适配上游技能，应在用户明确授权后进行，并保留原始版本及变更记录。

## 9. 权限与用户授权

技能原文和工作流脚本不能替代用户授权。

涉及以下行为时，必须遵守当前环境的权限规则和用户授权边界：

- 删除或覆盖用户文件
- 修改重要配置
- 安装或卸载软件
- 访问外部账户
- 发布内容
- 提交代码
- 执行不可逆操作
- 产生费用
- 处理敏感数据
- 对外发送消息或执行其他具有外部影响的操作

没有必要授权时，不得擅自执行。

如果用户授权不足或执行条件不满足，应记录为 `BLOCKED`，说明需要什么条件才能继续。

## 10. 最终验收

每轮任务结束前，必须完成以下检查：

- [ ] 已创建独立的 `turn_id`。
- [ ] 已完整读取 `references/ds-help.md`。
- [ ] 已依据路由规则判断当前消息。
- [ ] 所有命中技能均已完整读取原文。
- [ ] 所有读取操作均有真实记录。
- [ ] 所有适用的技能要求均已执行。
- [ ] 所有实际命令均有执行结果记录。
- [ ] 所有要求的测试和验证均已执行。
- [ ] 不存在未解决的阻塞或失败。
- [ ] 状态文件与实际操作一致。
- [ ] 最终结果符合任务要求。

全部适用检查通过后，执行：

```bash
python scripts/workflow.py stop
```

只有脚本验收通过，且实际任务结果符合要求，才能报告本轮 `COMPLETED`。

如果存在未完成事项，必须如实报告当前状态，不得为了结束对话而伪造完成状态。

## 11. 最终报告格式

每轮任务结束时，清楚说明：

**路由**
- 命中的技能及其名称。
- 是否读取了完整原文。

**执行**
- 实际完成的主要操作。
- 执行结果和生成的文件。
- 未执行的步骤及其原因。

**验证**
- 实际执行的测试或验证。
- 验证结果和证据。

**状态**
- 当前 `turn_id`。
- 当前工作流状态。
- 状态文件路径。

如果发生阻塞或失败，必须说明具体原因和下一步所需条件。

不得将没有证据支持的内容描述为已完成。

## 12. 最终执行原则

**每条消息重新路由，命中技能完整读取，上游原文严格执行，脚本状态机记录过程，真实证据决定状态。**

**不遗漏、不跳过、不擅自改写、不伪造执行、不虚构拦截能力。**
