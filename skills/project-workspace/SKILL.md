项目绑定，项目迁移，项目查询，资源同步。

## 功能

用户能主动触发的四件事：

| 功能 | 触发关键字 | 作用 |
|---|---|---|
| 项目绑定 | 开场自动、切到 X 工程、新建项目 | 让本会话绑定到某个工程目录 |
| 项目迁移 | 项目改名、合并工程、把 A 并到 B | 旧工程的文件搬到新工程 |
| 项目查询 | 有哪些项目、我在哪个项目 | 工程清单、当前工程路径 |
| 资源同步 | 同步技能、同步记忆 | app 内与外部镜像双向补齐 |

各节只讲怎么做。**完整参数、退出码、`--json` 结构、sync 语义与已知限制见 [`references/commands.md`](references/commands.md)**，需要时再读。

## 项目绑定

开场自动执行，不需要用户开口：

```sh
python3 /var/minis/skills/project-workspace/scripts/ws.py auto
```

按分组名找工程：存在就绑定，不存在就建空目录再绑定，最后列出目录内容作为上下文。首次使用会顺带准备好挂载下的 `projects/` 与 `skills/`。

| 输出 | 应对 |
|---|---|
| `＋ 已创建工程并关联` | 一句话告知路径，本次产物直接写进去 |
| `✅ 已关联工程` + 目录内容 | 把这份内容当工程上下文；要细节再按需读文件 |
| `ℹ️ 当前关联的是 A，但分组名是 B` | 用户可能改过分组名，问一句要不要迁移 |
| `本会话未分组` | 不建工程，静默按「执行约束」处理 |
| `没有找到外部挂载` (rc 3) | 提示去 [设置 → 挂载外部文件夹](minis://settings/mount-external)，本会话按默认逻辑继续 |
| `分组名不能直接当工程名` (rc 2) | 告知分组名含 `/` 或以 `.` 开头，建议改名 |

用户中途换工程或另建一个：

```sh
ws.py new <名>      # 建空目录并绑定本会话；重名 rc=1
ws.py link <名>     # 只绑定已存在的工程；不存在 rc=1
```

## 项目迁移

```sh
ws.py migrate                    # 免参数：按当前分组自动推断（推荐）
ws.py migrate <旧> <新>          # 显式新旧名
ws.py migrate <新>               # 旧名取当前绑定
ws.py migrate --dry              # 只预演，不动文件
```

| 旧工程 | 新工程 | 结果 |
|---|---|---|
| 无 | 有 | **复用**已有新工程，不复制；切换关联 |
| 无 | 无 | **创建**空的新工程；切换关联 |
| 有 | 无 | 建新工程并**复制**全部文件 |
| 有 | 有 | **复制合并**进新工程；任一同名路径 → rc=1 全部中止 |

**旧工程一律保留**：一个分组下有多个会话，别的会话可能还指着旧目录。复制完只在输出里提示"旧工程保留，确认无用后手动删除"，不自动清理。

旧工程不存在时要**明确告知**"没有可复制的内容"，再按上表复用或创建，不要静默跳过。

同名不代表内容相同——脚本不替你判断谁该留下，也不"跳过重复文件"后删旧目录。

**用户说「我改了项目名 / 分组名」时，直接跑零参数迁移，不要问任何名字：**

```sh
ws.py migrate          # 新名=当前 App 分组名，旧名=上次绑定（.project-prev / .project）
ws.py migrate --dry    # 只预演
```

1. 用户在 App 改了分组名 → 当前分组名就是新名，脚本自己查得出来，**不要问「新名字叫什么」**。
2. `rc=4`（没有旧工程线索）→ 先跑 `ws.py auto`（它会把旧名落盘到 `.project-prev`），再跑一次 `migrate`。
3. `rc=1`（文件冲突）→ 把冲突清单原样报给用户，不要自动覆盖任何一边。
4. 成功后提醒：App 里的会话分组要跟新工程同名；旧工程没有删除。

显式指定仍可用：`ws.py migrate <旧> <新>`、`ws.py migrate <新>`（旧名取当前绑定）。

- 迁移是破坏性的：名字不确定先 `--dry`；冲突清单原样报给用户，不要自作主张合并或覆盖任何一边。
- 会话分组是 App 侧标签，不随迁移改名；提醒用户同步改，否则下次开场会按旧名重建空目录。
- 冲突判定、`--dry` 输出格式、失败退出码见 `references/commands.md`。

## 项目查询

```sh
ws.py list      # 全部工程，标出当前绑定
ws.py which     # 当前会话的工程路径；未绑定 rc=4
```

报告工程内容时**逐行照抄 `auto` 的输出**，每行是 `相对路径 · 大小/项数` 的形式，例如 `666/ · 1 项` 与 `666/a.exe · 18.5 MB`。保留完整路径，不要重排成扁平列表、不要改成缩进树、不要凭印象改写「空目录」这类判断。

`list` 只列 `<挂载>/projects/` 下的目录。`<挂载>/skills/` 是技能镜像，里面也有 `quota-usage`、`project-workspace` 这类同名目录——**那是技能，不是工程**，不要混着报给用户。

## 资源同步

```sh
ws.py sync          # 只补缺失 + 记忆取新
ws.py sync --push   # 以 app 为准覆盖外部（改完本技能后跑）
ws.py sync --pull   # 以外部为准覆盖 app
ws.py sync --dry    # 只看要做什么
```

## 执行约束

不是功能，是每个功能都必须遵守的边界。

**产物落点**——绑定在工程里就全写进工程目录：

| 会话是否在工程中 | 产物写哪 |
|---|---|
| 在（`which` rc=0） | **全部**写进 `<挂载>/projects/<工程>/`，子目录按任务自建 |
| 不在（未分组 / 无挂载） | 草稿 `/var/minis/workspace/`，跨 chat 复用 `/var/minis/shared/` |

不要往 `workspace/` 或 `shared/` 放工程产物——那会让工程目录失真。

**工程必备**——工程目录只要两项：

| 必备 | 作用 |
|---|---|
| `.git` | 工程仓库，记录改动与决策 |
| `PROGRESS.md` | 现在到哪、下一步；为什么这样设计也写在这里 |

其余一律不建骨架。**会话产生的产物全部写进工程目录**，不往 `/tmp`、`workspace/`、`shared/` 放：交付物放根目录或按任务建子目录，中间稿、试错数据也留在工程里——工程在外部挂载上，由 git 管着，放到 `/tmp` 一重启就没，也进不了历史。跑测试用的隔离沙盒不算产物，可以用 `/tmp`，跑完即弃。

**命名**——工程名即目录名：单层、非隐藏、不含 `/` `\` `..`，否则 rc=2 拒绝。

**静默**——开场读到「未分组」不解释、不问用户，直接按上表默认逻辑走。

## 修改本技能后

这一节只管**本技能自己**——它是一份技能，所以要按写技能的规范维护；与它规定的「工程」是两回事，工程只需要 `.git` 与 `PROGRESS.md` 两项。

工作副本在 `<挂载>/projects/project-workspace/project-workspace/`，测试全绿才算修改完成。**不要直接改 `/var/minis/skills/` 下的文件**——那是部署产物，下次上线会被覆盖且不进历史。

1. 在工作副本里改，并在 `git commit` 前给 `tests/cases.json` 补对话级用例（格式见 `tests/README.md`）；
2. 在 `project-workspace/` 里提交：`git add -A && git commit -m "fix(ws): …"`（类型见上级目录 `WORKFLOW.md`）；
3. 回到上级目录跑 `python3 deploy.py`：先测，末行不是「失败 0 项」就拒绝上线；通过才同步 skills 并推镜像；
4. 上线后在 `PROJECT.md` 补一行改动摘要。
